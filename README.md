# Lemony Frontend

This is the React 19 + Vite + TypeScript client for Lemony (shown to players as **Lemonade Game**), built with Tailwind v4, Zustand, Socket.IO, Chart.js and react-three-fiber. The server computes every number. The client renders the state it receives and plays each day back.

## Run

```bash
npm ci
cp .env.example .env        # optional; Firebase web config is committed in firebase.ts
npm run dev                 # http://localhost:5173 — proxies /api and /socket.io to the backend on :8080
npm run build && npm run lint && npm run test:run
```

## How it fits together

| Area | Files |
|---|---|
| Identity | `firebase.ts`, `src/auth/AuthContext.tsx`: Google sign-in or guest. The socket stays disconnected until auth resolves (and while a visitor has no identity yet), and every handshake sends a fresh ID token or the guest id. A signed-in user whose token can't be fetched sends neither, never the guest id: the server refuses that handshake and the client tries again every 5 s while signed in. A guest with a game in progress is asked before signing in, since that game does not carry over to the account (`auth/confirmGuestSignIn.ts`). Only a signed-in user can sign out (`Layout`'s **Sign out**; `logout()` does nothing without a Firebase user); a guest sees **Sign in** instead and leaves guest mode only by signing in, so the guest id stays on the browser until then (`game_stack.md`, "Only signed-in users sign out"). |
| Socket | `src/api/socket.ts` sets up the connection. `src/api/socketHandlers.ts` registers every listener once, before React renders, and re-emits `resume_game` on every connect. The reconnect loop never gives up (at most 10 s between tries); while a dropped link is down the play screen shows a "Connection lost. Reconnecting…" notice (`shared/ReconnectingNotice`, from `store/connection.ts`), and whenever the socket is not connected the stand can't be opened, so no plan is sent into the void. That is how a refresh or a dropped connection gets back to the game; a day being watched then reopens on its report, since the server sends a day's customers once (`day_result.events`, `null` when it no longer has them) and keeps none. |
| Store | `src/store/gameStore.ts` is the single store and is written only by socket handlers. It drops any event whose `seq` is not newer than the last one applied, unless it is about another game than the one held (each game counts from its own start). A `NO_GAME` refusal (the game was replaced or abandoned elsewhere) clears the store and asks `resume_game` for whatever this identity plays now. The exception is `plan_preview`, the request-scoped what-if reply: it has no `seq`, and only the latest `request_id`'s reply is kept. It also remembers a failed save (`game_persist_failed`): the end screen then offers a retry, and "Play again" only once the game is saved. The server retries a failed save on its own too (2, 10 and 30 s later) and sends `game_persisted` when one works. |
| Rules and figures | The server owns them and computes every figure the client shows. Every bound comes as `limits` with the config defaults and every game state. The plan screen's spend, cash after, units, pack prices, cost and margin per cup and what-if curve come from `plan_preview` and the state; the day report, end screen and profile read server fields (success rates, cash at the start of each day, totals); the config screen and its help read `POST /config/preview` (including the busiest day's customers, `customers_per_day`, shown beside the served cap `limits.customers_per_day`). The client copies no formula (`noClientFormulas.test.ts`), and only formats, lays out and charts. |
| Routes | Each file in `src/pages/*` exports `route`, and `routes/registry.ts` discovers them. Pages: `/`, `/home`, `/new` (config), `/play`, `/profile`, `/profile/games/:gameId` (the owner's view of a saved game), `/results/:publicId`, `/credits`. `/results/:publicId` is a finished game's one results URL: public (no sign-in), never expiring, loaded from the server's stored copy (`GET /api/v1/games/id/{publicId}/results`), and linked from the end screen once the game is saved and from the owner's profile game page. |
| Playback | `src/game/timeline.ts` is pure. An actor's position is a function of the clock and its arrival minute, so changing speed, pausing or skipping needs no extra state. |
| Boards | `components/board2d/Board2D.tsx` is the 2D view. `components/board3d/*` is the 3D view: it is lazy-loaded in its own chunk, has a pure `sceneModel.ts`, uses the GLB models in `public/3dmodels` (CC-BY, see `/credits`), and falls back to 2D on any WebGL failure. |
| Charts | `components/charts/*` is the chart kit: the validated dataviz palette, `ChartBox`, a DOM `Legend`, a crosshair shared across a group of charts, and reference rules drawn without being datasets. Every chart has a single y-axis, an x-axis title and a table view. The end screen's charts are in `components/charts/endgame/`. The morning plan's what-if curve (`components/plan/WhatIfChart.tsx`) is drawn from the server's `plan_preview` reply. |
